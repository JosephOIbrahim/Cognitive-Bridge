    10→## Abstract
    11→
    12→We present the USD Cognitive Substrate, a novel architecture that repurposes Universal Scene Description (USD) composition semantics—originally designed for conflict resolution in visual effects pipelines—for deterministic state management in large language model (LLM) applications. The architecture achieves a previously elusive property: **fully deterministic cognitive behavior** from signal detection through response generation, with stochasticity isolated exclusively to irreducible human input/output boundaries.
    13→
    14→The system comprises two orthogonal hierarchies: a USD Composition Hierarchy for state storage with LIVRPS (Local, Inherits, VariantSets, References, Payloads, Specializes) resolution, and a Runtime Service Stack for processing, routing, and adaptation. A novel "Mycelium" mechanism provides neuroplasticity within constitutional bounds, enabling the system to learn while maintaining safety guarantees.
    15→
    16→**Version 7.0.0 introduces three major extensions:**
    17→1. **Grounding Layer (L7.5)** — The "ACCESS over LEARN" paradigm: route queries to deterministic oracles (physics simulators, knowledge graphs) when ground truth exists
    18→2. **BCM Stigmergic Learning** — Bienenstock-Cooper-Munro learning with trail-based expert confidence as *metadata annotation only*, preserving ThinkingMachines batch-invariance
    19→3. **Signal Reliability Tracking** — Fingerprint-outcome correlation for routing confidence prediction
    20→
    21→When integrated with batch-invariant inference engines (ThinkingMachines), the architecture guarantees: **same user input + same state → same response + same state update**. This enables reproducible sessions, behavioral unit testing, complete audit trails, and formally verifiable cognitive systems.
    22→
    23→**Keywords:** Universal Scene Description, cognitive architecture, deterministic AI, state management, neuroplasticity, batch invariance, LIVRPS composition, grounded world models, BCM learning

    27→## 1. Introduction
    28→
    29→### 1.1 The Problem
    30→
    31→Modern LLM applications face a fundamental tension: users expect consistent, personalized behavior, but LLM inference is inherently stochastic. The same prompt can produce different outputs based on:
    32→
    33→- Batch size during inference
    34→- Server load affecting reduction order
    35→- Non-deterministic GPU operations
    36→- Temperature and sampling parameters
    37→
    38→This non-determinism creates challenges for:
    39→
    40→1. **Debugging** — Cannot reproduce reported issues
    41→2. **Testing** — Behavioral tests are flaky
    42→3. **Auditing** — Cannot verify decision traces
    43→4. **Personalization** — Learning is noisy
    44→5. **Safety** — Cannot guarantee behavioral bounds
    45→
    46→### 1.2 The Thesis
    47→
    48→We propose that **USD (Universal Scene Description) composition semantics are uniquely suited for cognitive state management in LLM applications**. This is not about using USD for 3D graphics—it is about repurposing USD's conflict resolution system for AI state management.
    49→
    50→The parallel:
    51→
    52→| VFX Problem | AI Problem |
    53→|-------------|------------|
    54→| Multiple departments (model, rig, anim, light) disagree about scene data | Multiple state sources (profile, mood, task, safety) disagree about behavior |
    55→| USD's LIVRPS resolves conflicts deterministically | USD's LIVRPS resolves conflicts deterministically |
    56→
    57→Same solution. Different domain.
    58→
    59→### 1.3 Contributions
    60→
    61→This paper makes the following contributions:
    62→
    63→1. **Separation of Storage and Routing** — USD provides state persistence; a separate routing engine provides adaptive behavior
    64→
    65→2. **The Mycelium Mechanism** — A neuroplasticity system with four rebalancing avenues (activation spreading, Hebbian learning, attractor dynamics, homeostatic regulation) operating within hard constitutional bounds
    66→
    67→3. **The Mycelium Arc** — A novel USD composition arc for horizontal (agent-to-agent) state flow, complementing LIVRPS's vertical composition
    68→
    69→4. **Determinism Analysis** — Formal identification of stochastic boundaries and requirements for full reproducibility
    70→
    71→5. **Integration with Batch-Invariant Inference** — When combined with ThinkingMachines kernels, the architecture achieves full determinism except for irreducible human I/O
    72→
    73→**v7.0.0 Additional Contributions:**
    74→
    75→6. **Grounding Layer (L7.5)** — The "ACCESS over LEARN" paradigm for deterministic ground truth via oracle integration (validated: 10/10 experiments, physics + constraint satisfaction)
    76→
    77→7. **BCM Stigmergic Learning** — Trail-based expert confidence with Bienenstock-Cooper-Munro saturation, providing learning capability while maintaining batch-invariance through queued updates
    78→
    79→8. **Plasticity Auto-Triggers** — Adaptive learning rate windows that open during crashes and close on convergence
    80→
    81→9. **Signal Reliability Tracking** — Fingerprint-outcome correlation for predictive routing confidence

    85→## 2. Background
    86→
    87→### 2.1 Universal Scene Description (USD)
    88→
    89→USD is Pixar's open-source framework for describing, composing, and querying hierarchical scene data. Its key properties relevant to our work:
    90→
    91→**LIVRPS Composition Order:**
    92→- **L**ocal — Direct opinions on a prim (highest priority)
    93→- **I**nherits — Inherited from parent prims
    94→- **V**ariantSets — Selected variants
    95→- **R**eferences — External file references
    96→- **P**ayloads — Lazy-loaded external content
    97→- **S**pecializes — Base class inheritance (lowest priority)
    98→
    99→**Key Properties:**
   100→1. **Native Composition** — Conflict resolution is built into the format
   101→2. **Lazy Loading (Payloads)** — Content loads on demand
   102→3. **First-Class Variants** — Mode switching is a language construct
   103→
   104→No other configuration format (JSON, YAML, Protobuf, GraphQL) provides all three properties.
   105→
   106→### 2.2 Determinism in LLM Inference
   107→
   108→**The Key Insight**: Individual LLM forward passes are run-to-run deterministic. The source of user-visible nondeterminism is that **batch size varies with server load**, and most kernels lack batch-invariance.
   109→
   110→ThinkingMachines (2025) demonstrated this empirically: **80 unique completions from 1000 identical requests** at temperature=0. The variation occurs because:
   111→
   112→1. **Batch-size-dependent reduction order** — The same matrix operation (`torch.mm(a[:1], b)` vs `torch.mm(a, b)[:1]`) produces different results depending on batch size, even though the mathematical operation is identical
   113→2. **Load-dependent batching** — Server load determines batch size, introducing runtime variation
   114→3. **Kernel optimization switches** — Some kernels change algorithms (e.g., split-K) based on batch size
   115→
   116→**What doesn't fully explain it** (common misconceptions):
   117→- Floating-point non-associativity alone (individual kernels can be deterministic)
   118→- GPU thread scheduling (can be controlled)
   119→- Sampling randomness (can be seeded)
   120→
   121→ThinkingMachines batch-invariant kernels eliminate these sources at a cost of ~1.6-2.1x performance overhead (1.6x with optimized attention kernel, 2.1x unoptimized).
   122→
   123→### 2.3 Cognitive Architectures
   124→
   125→Prior cognitive architectures (ACT-R, SOAR, LIDA) provide theoretical frameworks for cognitive modeling but lack:
   126→
   127→1. **Deterministic guarantees** — Behavior varies across runs
   128→2. **Persistent composition** — State management is ad-hoc
   129→3. **Lazy expertise loading** — All knowledge must be present
   130→4. **Constitutional bounds** — Safety constraints are not first-class

   134→## 3. Architecture Overview
   135→
   136→The USD Cognitive Substrate comprises two orthogonal hierarchies:
   137→
   138→```
   139→┌─────────────────────────────────────────────────────────────────────────┐
   140→│                      RUNTIME SERVICE STACK                               │
   141→│  (Processing, Routing, Adaptation, Dispatch)                            │
   142→│                                                                          │
   143→│  R1: Application Layer ─── External apps reporting signals              │
   144→│  R2: Intervention Dispatch ─── Expert → application-specific actions    │
   145→│  R3: Signal Aggregator ─── Multi-source signal normalization            │
   146→│  R4: Routing Engine ─── Expert selection + neuroplasticity              │
   147→│  R5: Temporal Orchestrator ─── Session lifecycle + pattern learning     │
   148→│  R6: Context Restorer ─── "Where was I?" continuity                     │
   149→│                                                                          │
   150→└─────────────────────────────────────────────────────────────────────────┘
   151→                               ↕ reads/writes
   152→┌─────────────────────────────────────────────────────────────────────────┐
   153→│                      USD COMPOSITION HIERARCHY                           │
   154→│  (State Storage with LIVRPS Resolution)                                 │
   155→│                                                                          │
   156→│  L13: current.usda ─────────────────────────────────── [LOCAL]          │
   157→│  L12: snapshots/*.usda ─────────────────────────────── [LOCAL]          │
   158→│  L11: daily/*.usda ─────────────────────────────────── [INHERITS]       │
   159→│  L10: weekly/*.usda ────────────────────────────────── [INHERITS]       │
   160→│  L9:  calibration.usda ─────────────────────────────── [REFERENCES]     │
   161→│  L8:  profile.usda ─────────────────────────────────── [SPECIALIZES]    │
   162→│  L7:  payloads/*.usda ──────────────────────────────── [PAYLOADS]       │
   163→│                                                                          │
   164→└─────────────────────────────────────────────────────────────────────────┘
   165→```
   166→
   167→**Critical Design Decision:** USD provides storage and composition semantics. USD does NOT provide routing logic. The routing engine is a separate layer that reads from and writes to USD.

   171→## 4. USD Composition Hierarchy
   172→
   173→### 4.1 Layer Definitions
   174→
   175→| Layer | USD Arc | Mutability | Contents |
   176→|-------|---------|------------|----------|
   177→| L13: current.usda | LOCAL | Mutable | Live session state: energy, momentum, expert_weights, active task |
   178→| L12: snapshots/*.usda | LOCAL | Immutable | Context restoration points with task, cognitive, environmental state |
   179→| L11: daily/*.usda | INHERITS | Append-only | Aggregated daily patterns, time-of-day weights |
   180→| L10: weekly/*.usda | INHERITS | Append-only | Day-of-week patterns, weekly rhythms |
   181→| L9: calibration.usda | REFERENCES | Slow-update | Long-term learned weight adjustments, temporal patterns |
   182→| L8: profile.usda | SPECIALIZES | Immutable | Base traits, safety floors, constitutional constraints |
   183→| L7: payloads/*.usda | PAYLOADS | Immutable | Domain specializations (ADHD, Anxiety, VFX, etc.) |
   184→
   185→### 4.2 LIVRPS Resolution
   186→
   187→**Figure 2: LIVRPS Composition Resolution**
   188→
   189→```
   190→                    QUERY: "What is energy?"
   191→                              │
   192→                              ▼
   193→┌─────────────────────────────────────────────────────────────────────┐
   194→│  LIVRPS RESOLUTION ORDER (Strongest → Weakest)                      │
   195→├─────────────────────────────────────────────────────────────────────┤
   196→│                                                                     │
   197→│  L: LOCAL ──────────────► current.usda ──────► energy = 0.3 ✓ WINS │
   198→│     (highest priority)                                              │
   199→│            │                                                        │
   200→│            ▼ if not found                                           │
   201→│  I: INHERITS ──────────► daily/*.usda ───────► (not set)           │
   202→│            │                                                        │
   203→│            ▼ if not found                                           │
   204→│  V: VARIANTSETS ────────► mode_variants ─────► (not set)           │
   205→│            │                                                        │
   206→│            ▼ if not found                                           │
   207→│  R: REFERENCES ─────────► calibration.usda ──► energy = 0.7        │
   208→│            │                                                        │
   209→│            ▼ if not found                                           │
   210→│  P: PAYLOADS ───────────► adhd.usda ─────────► (not set)           │
   211→│            │                                                        │
   212→│            ▼ if not found                                           │
   213→│  S: SPECIALIZES ────────► profile.usda ──────► energy = 0.5        │
   214→│     (lowest priority)        (default)                              │
   215→│                                                                     │
   216→└─────────────────────────────────────────────────────────────────────┘
   217→                              │
   218→                              ▼
   219→                    RESULT: energy = 0.3
   220→                    (from LOCAL: current.usda)
   221→```
   222→
   223→**Resolution Rule:** First layer with a defined value wins. Higher layers shadow lower layers without modifying them.
   224→
   225→**Exception:** Constitutional constraints in profile.usda (SPECIALIZES) cannot be overridden by any layer—they are protected by the substrate itself.

   294→## 5. Runtime Service Stack
   295→
   296→### 5.1 Signal Aggregator (R3)
   297→
   298→Collects signals from multiple applications with priority ordering:
   299→
   300→```
   301→Priority  Category    Description
   302→────────  ──────────  ─────────────────────────────
   303→1         SAFETY      Requires immediate protective response
   304→2         AFFECTIVE   Emotional state signals
   305→3         MODE        Cognitive mode transitions
   306→4         DOMAIN      Task-domain triggers (from payloads)
   307→5         CONTENT     Informational/task content
   308→```
   309→
   310→**Aggregation Rules:**
   311→1. Temporal weighting (recent > old)
   312→2. Safety signals bypass queue
   313→3. Source trust weighting
   314→4. Consensus detection (multiple sources = higher confidence)
   315→5. Conflict resolution (higher category wins)
   316→
   317→### 5.2 Routing Engine (R4) — 8-Phase NEXUS Pipeline (v7.0.0)
   318→
   319→Eight-phase routing with deterministic properties and grounding support:
   320→
   321→**Figure 1: 8-Phase NEXUS Routing Flow (v7.0.0)**
   322→
   323→```
   324→                            USER INPUT
   325→                                │
   326→                                ▼
   327→┌───────────────────────────────────────────────────────────────────────┐
   328→│  PHASE 0: RETRIEVE (Fast Path)                                        │
   329→│  Knowledge check for factual queries → O(1) retrieval                 │
   330→│  IF confidence ≥ 0.85: Return directly (skip phases 0b-5)             │
   331→└───────────────────────────────────────────────────────────────────────┘
   332→                                │
   333→                                ▼
   334→┌───────────────────────────────────────────────────────────────────────┐
   335→│  PHASE 0b: CLASSIFY (v7.0.0 - Grounding)                              │
   336→│  Determine source mode: LEARN | ACCESS | HYBRID                       │
   337→│  Grounding signals: physics, simulate, position, velocity, collision  │
   338→└───────────────────────────────────────────────────────────────────────┘
   339→                                │
   340→                                ▼
   341→┌───────────────────────────────────────────────────────────────────────┐
   342→│  PHASE 0c: GROUND (v7.0.0 - Oracle Query)                             │
   343→│  IF source_mode ∈ {ACCESS, HYBRID}:                                   │
   344→│    Query oracle registry → Execute deterministic query                │
   345→│    Cache result with provenance (confidence = 1.0)                    │
   346→└───────────────────────────────────────────────────────────────────────┘
   347→                                │
   348→                                ▼
   349→┌───────────────────────────────────────────────────────────────────────┐
   350→│  PHASE 1: DETECT (formerly ACTIVATE)                                  │
   351→│  ┌─────────────┐    ┌──────────────────┐    ┌──────────────────────┐ │
   352→│  │   Signal    │───▶│  PRISM + BCM     │───▶│  Activation Vector   │ │
   353→│  │  "stuck"    │    │  Fingerprinting  │    │  [0,0.8,0,0,0,0.2,0] │ │
   354→│  └─────────────┘    └──────────────────┘    └──────────────────────┘ │
   355→└───────────────────────────────────────────────────────────────────────┘
   356→                                │
   357→                                ▼
   358→┌───────────────────────────────────────────────────────────────────────┐
   359→│  PHASE 2: CASCADE (formerly WEIGHT)                                   │
   360→│  Safety gates → ADHD_MoE → GROUNDING_MoE → BCM confidence             │
   361→│  activation × expert_weights × bcm_trail_modifier = weighted_scores   │
   362→└───────────────────────────────────────────────────────────────────────┘
   363→                                │
   364→                                ▼
   365→┌───────────────────────────────────────────────────────────────────────┐
   366→│  PHASE 3: LOCK (formerly BOUND)                                       │
   367→│  ┌────────────────────┐  ┌────────────────────┐  ┌────────────────┐  │
   368→│  │  Safety Floors     │  │  Homeostatic Norm  │  │  Parameter +   │  │
   369→│  │  max(w, floor)     │─▶│  w / sum(w) = 1.0  │─▶│  BCM Lock      │  │
   370→│  │  Validator ≥ 0.10  │  │                    │  │  (no variance) │  │
   371→│  └────────────────────┘  └────────────────────┘  └────────────────┘  │
   372→└───────────────────────────────────────────────────────────────────────┘
   373→                                │
   374→                                ▼
   375→┌───────────────────────────────────────────────────────────────────────┐
   376→│  PHASE 4: EXECUTE (formerly SELECT)                                   │
   377→│  expert = argmax(bounded_scores)                                      │
   378→│  Tiebreaker: lower priority index wins                                │
   379→│  Generate with locked params + oracle results (if grounded)           │
   380→└───────────────────────────────────────────────────────────────────────┘
   381→                                │
   382→                                ▼
   383→┌───────────────────────────────────────────────────────────────────────┐
   384→│  PHASE 5: UPDATE (Mycelium + BCM + Plasticity)                        │
   385→│  ┌─────────────┐    ┌─────────────┐    ┌─────────────────────────┐   │
   386→│  │  Outcome    │───▶│  Hebbian +  │───▶│  BCM Trail Update       │   │
   387→│  │  (0.0-1.0)  │    │  BCM Queue  │    │  (QUEUED, not applied)  │   │
   388→│  └─────────────┘    └─────────────┘    └─────────────────────────┘   │
   389→│  Plasticity auto-trigger check: momentum=CRASHED → open window       │
   390→└───────────────────────────────────────────────────────────────────────┘
   391→                                │
   392→                                ▼
   393→┌───────────────────────────────────────────────────────────────────────┐
   394→│  [POST] FLUSH (v7.0.0 - BCM Batch-Invariance)                         │
   395→│  Batch apply all queued trail updates AFTER processing completes     │
   396→│  Ensures: same inputs → same routing (trails are metadata only)       │
   397→└───────────────────────────────────────────────────────────────────────┘
   398→                                │
   399→                                ▼
   400→                          EXPERT RESPONSE
   401→```
   402→
   403→**Determinism Guarantee:** Each phase is individually deterministic. Given identical input signal and state, the routing produces identical expert selection. BCM trail updates are QUEUED and applied AFTER processing, ensuring batch-invariance.
   404→
   405→**Phase Details (v7.0.0):**
   406→
   407→```
   408→Phase 0: RETRIEVE (Fast Path)
   409→  Factual query detection ("what is", "explain", "define")
   410→  O(1) knowledge graph lookup (~0.001ms)
   411→  Confidence ≥ 0.85 → Return directly (skip remaining phases)
   412→  Deterministic (fixed triggers, fixed graph structure)
   413→
   414→Phase 0b: CLASSIFY (Grounding)
   415→  Detect grounding signals (physics, simulate, position, etc.)
   416→  Determine source mode: LEARN | ACCESS | HYBRID
   417→  Deterministic (fixed signal patterns)
   418→
   419→Phase 0c: GROUND (Oracle Query)
   420→  If ACCESS/HYBRID: Query oracle registry
   421→  Execute deterministic oracle (e.g., Houdini RBD, Bullet physics)
   422→  Cache result with provenance
   423→  Deterministic (oracle is bit-identical, cache is hash-based)
   424→
   425→Phase 1: DETECT
   426→  Signal → PRISM Pattern Match → Activation Vector
   427→  BCM signal fingerprint capture (QUEUED, not used in routing)
   428→  Deterministic given fixed pattern dictionary (L0D)
   429→
   430→Phase 2: CASCADE
   431→  Safety gates → ADHD_MoE → GROUNDING_MoE (if applicable)
   432→  weighted = activation × expert_weights
   433→  BCM confidence is METADATA ANNOTATION only (does NOT affect selection)
   434→  Deterministic (element-wise multiplication)
   435→
   436→Phase 3: LOCK
   437→  Apply safety floors (expert_weights >= safety_floors)
   438→  Apply homeostatic limits (normalize to sum = 1)
   439→  Lock parameters + grounding sources BEFORE generation
   440→  Deterministic (fixed bounds, explicit locking)
   441→
   442→Phase 4: EXECUTE
   443→  expert = argmax(bounded_weighted)
   444→  Tiebreaker: lower index wins
   445→  Generate using locked params + oracle results
   446→  Deterministic
   447→
   448→Phase 5: UPDATE
   449→  Hebbian learning, attractor dynamics, RC^+xi convergence
   450→  BCM trail updates QUEUED (not applied during processing)
   451→  Plasticity window check (CRASHED → open, CONVERGED → close)
   452→  Deterministic given outcome
   453→
   454→[POST] FLUSH
   455→  Apply queued BCM trail updates
   456→  Apply fingerprint-outcome correlations
   457→  Happens AFTER response delivered
   458→  Ensures batch-invariance: same inputs → same routing
   459→```
   460→
   461→### 5.3 Expert Archetypes

   614→- α = learning rate (from calibration)
   615→- outcome = measured result [-1, 1]
   616→- expected = baseline expectation
   617→- activation = how strongly this expert was used

   624→Basins: convergent, divergent, recovery, transfer
   625→
   626→State vector: [energy, momentum, load, coherence]
   627→Distance to each basin computed

   629→Transition thresholds prevent oscillation

   632→**Avenue 4: Homeostatic Regulation**
   633→
   634→System maintains equilibrium:
   635→
   636→```

   638→   → Increase Restorer weight
   639→
   640→IF focus_coherence declining:

   642→
   643→IF cognitive_load > threshold:
   644→   → Increase Scaffolder weight

   647→### 6.3 Bound Enforcement
   648→
   649→All dynamic adaptation is constrained:
   650→
   651→1. Safety floors are hard minimums
   652→2. Weights are normalized after every update
   653→3. Constitutional constraints cannot be violated
   654→4. Learning cannot exceed rate limits
   655→
   656→### 6.4 Formal Mathematical Specification
   657→
   658→**Definition 1 (Weight Space)**
   659→Let W = {w ∈ ℝ^7 | w_i ≥ f_i ∀i ∈ [1,7], Σw_i = 1}
   660→where f = [0.10, 0.05, 0.05, 0, 0, 0, 0] are safety floors.
   661→
   662→**Definition 2 (Activation Function)**
   663→A: T × C → ℝ^7 where T is task space, C is context space.
   664→A(t, c)_i = min(|{p ∈ triggers_i : p ⊆ t}| / |triggers_i|, 1.0)
   665→
   666→**Definition 3 (Hebbian Update)**
   667→U: W × ℝ × ℝ^7 → W
   668→U(w, o, a)_i = clip(w_i + α(o - e)a_i, f_i, 1.0) / Z
   669→where Z normalizes to sum=1, α ∈ (0, 0.2], o ∈ [-1, 1], e = 0.5
   670→
   671→**Theorem 1 (Safety Floor Invariant)**
   672→∀w ∈ W, ∀o, a: U(w, o, a) ∈ W
   673→*Proof*: By construction, clip enforces w_i ≥ f_i, and Z normalizes sum to 1. ∎
   674→
   675→**Theorem 2 (Bounded Learning)**
   676→|U(w, o, a)_i - w_i| ≤ α × max(|o - e|) × max(||a||_∞) ≤ 0.2 × 1 × 1 = 0.2
   677→*Proof*: By definition of clip and bounds on α, o, a. ∎
   678→
   679→**Theorem 3 (Convergence)**
   680→Under stationary outcome distribution, w converges to E[o × a] / Σ_i E[o × a_i].
   681→*Proof sketch*: Standard Hebbian convergence with decay. Full proof in Appendix D.
   682→
   683→### 6.5 BCM Stigmergic Reinforcement Learning (v7.0.0)
   684→
   685→**Core Principle: "Trails, Not Orders"**
   686→
   687→BCM (Bienenstock-Cooper-Munro) learning provides metadata about expert effectiveness but NEVER changes the deterministic routing order. This maintains ThinkingMachines batch-invariance.
   688→
   689→**Trail-Based Expert Confidence:**
   690→
   691→Each expert has a Trail tracking success rates:
   692→
   693→```python
   694→class OrchestraTrail:
   695→    expert_id: str
   696→    strength: float  # 0.01 - 100.0 (pheromone-like)
   697→    success_rate: float  # 0.0 - 1.0
   698→    total_outcomes: int
   699→    successful_outcomes: int
   700→
   701→    @property
   702→    def confidence(self) -> float:
   703→        return 0.6 * self.success_rate + 0.4 * (self.strength / 100.0)
   704→```
   705→
   706→**BCM Saturation (Homeostasis):**
   707→
   708→The sliding threshold θ_m decreases as activity increases, preventing unbounded growth:
   709→
   710→```
   711→θ_m(t) = θ_m(t-1) × decay_factor + (1 - decay_factor) × recent_activity
   712→saturation_factor = 1 / (1 + exp(-(strength - θ_m) / temperature))
   713→update = base_update × saturation_factor
   714→```
   715→
   716→**Time-Based Decay:**
   717→
   718→Trail strength decays exponentially with a 2-hour half-life:
   719→
   720→```
   721→decay = exp(-time_elapsed / half_life)
   722→new_strength = old_strength × decay
   723→```
   724→
   725→**ThinkingMachines Compliance (CRITICAL):**
   726→
   727→```
   728→✓ Trail updates QUEUED during processing (Phase 5)
   729→✓ Queued updates applied AFTER response delivered ([POST] FLUSH)
   730→✓ Same inputs → same routing (trails are metadata only)
   731→✓ BCM confidence annotates decisions, does NOT affect selection order
   732→✓ Batch-invariant: routing identical regardless of trail state
   733→```

  1061→### 8.2 With ThinkingMachines
  1062→
  1063→ThinkingMachines provides batch-invariant kernels that guarantee identical outputs regardless of batch size:
  1064→
  1065→| Operation | Batch-Invariant Strategy | Performance Cost |
  1066→|-----------|-------------------------|------------------|
  1067→| **RMSNorm** | Data-parallel: assign each batch element to one core, maintaining identical reduction order regardless of batch size | Minimal |
  1068→| **Matrix Multiplication** | Fixed tensor-core instructions and tile sizes across all batch sizes; avoid split-K optimization | ~20% vs cuBLAS |
  1069→| **Attention** | Fixed split-SIZE (not split-count) for KV dimension; reduction order for a given token doesn't depend on batch | Optimized: 1.6x total |
  1070→
  1071→**Key Implementation Detail**: KV cache and page tables must be updated before the attention kernel to maintain consistent memory layout regardless of token processing strategy.
  1072→
  1073→**Result:** All LLM-dependent operations become deterministic. The same request produces identical output whether batch=1 or batch=1000.

  1355→## 13.4 Known Limitations
  1356→
  1357→1. **Keyword-Based Signal Detection**: Triggers rely on keyword matching. Semantic understanding requires LLM in the loop, reintroducing non-determinism. Future work: learned embeddings with quantized similarity.
  1358→
  1359→2. **Single-Model Assumption**: Current design assumes one LLM. Multi-model routing (e.g., different models for different experts) adds complexity not addressed in this specification.
  1360→
  1361→3. **Cold Start Problem**: New users have uniform weights. Initial sessions may have suboptimal routing until Hebbian learning accumulates data. Mitigation: Calibration wizard.
  1362→
  1363→4. **Memory vs. Compute Tradeoff**: ThinkingMachines batch-invariance has performance cost: 2.1x slowdown with unoptimized kernels, 1.6x with optimized attention. MatMul specifically costs ~20% vs cuBLAS. For latency-sensitive applications, this may require hybrid mode (deterministic for routing, probabilistic for generation).
  1364→
  1365→5. **USD Ecosystem Maturity**: While USD is an industry standard for VFX, its ecosystem outside VFX is nascent. Python pxr bindings are mature; other languages less so.

  1533→```python
  1534→def aggregate_confidences(instances, strategy, config):
  1535→    """
  1536→    Aggregate confidences with determinism guarantee.
  1537→    CRITICAL: Sort FIRST, then aggregate.
  1538→    """
  1539→    # CRITICAL: Sort first for determinism
  1540→    sorted_instances = sorted(
  1541→        instances,
  1542→        key=lambda i: deterministic_sort_key(i, config.aggregation_order)
  1543→    )
  1544→
  1545→    if strategy == "max":
  1546→        return max(i.confidence for i in sorted_instances)
  1547→
  1548→    elif strategy == "mean":
  1549→        # Kahan summation for batch-invariant accumulation
  1550→        return kahan_sum([i.confidence for i in sorted_instances]) / len(sorted_instances)
  1551→
  1552→    elif strategy == "weighted_mean":
  1553→        total_weight = sum(i.access_count for i in sorted_instances) or 1
  1554→        weighted = [i.confidence * i.access_count / total_weight for i in sorted_instances]
  1555→        return kahan_sum(weighted)
  1556→
  1557→    elif strategy == "threshold_filter":
  1558→        filtered = [i for i in sorted_instances if i.confidence >= config.threshold]
  1559→        return max(i.confidence for i in filtered) if filtered else 0.0
  1560→
  1561→
  1562→def kahan_sum(values):
  1563→    """Kahan summation for numerical stability (batch-invariant)."""
  1564→    total = 0.0
  1565→    compensation = 0.0
  1566→    for value in values:
  1567→        y = value - compensation
  1568→        t = total + y
  1569→        compensation = (t - total) - y
  1570→        total = t
  1571→    return total
  1572→```

  2221→## Appendix D: BCM Learning Mathematics
  2222→
  2223→**Bienenstock-Cooper-Munro Saturation:**
  2224→
  2225→The BCM sliding threshold provides homeostatic regulation:
  2226→
  2227→```
  2228→θ_m(t+1) = θ_m(t) × α + (1 - α) × ȳ²(t)
  2229→```
  2230→
  2231→Where:
  2232→- θ_m = sliding threshold
  2233→- α = decay factor (typically 0.95)
  2234→- ȳ = recent activity average
  2235→
  2236→**Trail Strength Update:**
  2237→
  2238→```
  2239→Δs = η × (y - θ_m) × x × saturation(s)
  2240→s_new = clip(s + Δs, 0.01, 100.0)
  2241→```
  2242→
  2243→Where:
  2244→- η = base learning rate
  2245→- y = outcome signal
  2246→- x = activation level
  2247→- saturation(s) = 1 / (1 + exp(-(s - θ_m) / T))
  2248→
  2249→**Time Decay:**
  2250→
  2251→```
  2252→s(t) = s(0) × exp(-t / τ)
  2253→τ = 2 hours (half-life)
  2254→```
