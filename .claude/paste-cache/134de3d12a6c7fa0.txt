### SCENE DOCTOR — `/diagnose`

**What it does:** Full health audit of the current scene. Not just listing
problems — offering to fix them.

**Checks (priority order):**

| Check | Severity | Auto-fixable? |
|-------|----------|--------------|
| Missing texture files | Critical | Yes — remap to $JOB paths |
| Broken node references | Critical | Yes — reconnect or flag |
| Unconnected required inputs | Error | Yes — suggest connections |
| Out-of-range parameters | Warning | Yes — clamp to valid range |
| Infinite cook dependencies | Critical | No — explain the cycle |
| Missing camera for render | Error | Yes — create default |
| Zero-area lights | Warning | Yes — set minimum size |
| Empty merge inputs | Warning | Yes — clean up |
| Unused nodes (no output path) | Info | No — just flag |
| Stale cache files | Info | Yes — clear |
| Non-square textures for tiling | Info | No — flag |
| Missing display/render flags | Warning | Yes — set on last node |

**Architecture:**

```
/diagnose
  → gather all nodes in scene (or current network)
  → for each node:
      check inputs connected
      check for cook errors (node.errors())
      check parameter values against metadata ranges
      check file paths exist on disk
  → for render context:
      check camera assignment
      check resolution set
      check output path writable
      check materials bound
  → compile report
  → display in chat with severity icons
  → offer batch fix: "Fix 7 auto-fixable issues?"
```

**Implementation: 2 files**

| File | Agent | Description |
|------|-------|-------------|
| `python/synapse/panel/scene_doctor.py` | INDIA | Diagnostic engine — runs checks, returns structured report |
| Panel integration | JULIET | Wire /diagnose command, display report, handle fix-it flow |

**MOE Prompt — AGENT INDIA (Scene Doctor Engine):**

```
I need you to create a scene diagnostic engine for SYNAPSE.

CONTEXT:
- Repo root: C:\Users\User\SYNAPSE
- SYNAPSE runs inside Houdini 21 with full hou module access
- The panel can execute tools on the main thread via SynapseHandler
- Artists need a /diagnose command that finds and fixes scene problems

YOUR TASK:
Create python/synapse/panel/scene_doctor.py

REQUIREMENTS:

1. Function diagnose_scene(scope: str = "all") -> DiagnosticReport
   scope: "all" | "current_network" | "render" | "materials"

   Returns a DiagnosticReport dataclass:
   @dataclass
   class DiagnosticIssue:
       severity: str     # "critical", "error", "warning", "info"
       category: str     # "missing_file", "broken_ref", "bad_parm", etc.
       node_path: str    # affected node
       message: str      # human-readable description
       fix_available: bool
       fix_description: str  # what the fix would do
       fix_fn: Optional[Callable]  # function that fixes it (called on main thread)

   @dataclass
   class DiagnosticReport:
       issues: List[DiagnosticIssue]
       nodes_checked: int
       time_elapsed: float
       summary: str  # "Found 12 issues: 2 critical, 3 errors, 5 warnings, 2 info"

2. Individual check functions (each returns list of DiagnosticIssue):
   - check_missing_files(nodes) — textures, alembics, file SOPs
   - check_broken_inputs(nodes) — unconnected required inputs
   - check_cook_errors(nodes) — nodes with existing cook errors
   - check_parameter_ranges(nodes) — values outside metadata min/max
   - check_render_readiness() — camera, resolution, output path, materials
   - check_circular_deps(nodes) — infinite cook loops
   - check_unused_nodes(nodes) — nodes with no downstream consumers
   - check_display_flags(network) — missing display/render flags
   - check_empty_merges(nodes) — merge nodes with disconnected inputs

3. Function apply_fixes(issues: List[DiagnosticIssue]) -> dict
   Applies all auto-fixable issues. Returns {fixed: int, failed: int, skipped: int}.
   Wraps everything in an undo group.

4. hou import is required but wrapped in try/except at module level.
   If hou unavailable, diagnose_scene returns empty report.

5. ALL hou calls must be safe for the main thread. Use node.errors(),

6. File existence checks should handle $JOB, $HIP, $HOME variable expansion
   using hou.text.expandString() or hou.expandString().

7. Performance: must complete full scene audit in <5 seconds for 500-node scenes.
   Short-circuit expensive checks on large scenes.

VERIFY:
- Read python/synapse/server/handlers.py for patterns of hou.* usage
- The module will be called from the main thread by the panel
- Run: python -c "from synapse.panel.scene_doctor import DiagnosticReport; print('OK')"
  (Will work outside Houdini for import check — actual diagnosis needs hou)

DO NOT modify existing files. Only create python/synapse/panel/scene_doctor.py
```

**What it does:** Pre-render checklist that catches the problems that waste
overnight farm hours. This is the feature pipeline TDs dream about.

**Checks:**

| Check | What It Catches |
|-------|----------------|
| Memory estimation | "This scene will need ~48GB RAM. Your machine has 32GB." |
| Texture resolution audit | "8K texture on a background element 200px in frame. Suggest 1K." |
| Light sampling analysis | "Area light with 1 sample — will be noisy. Suggest 4-16." |
| Motion blur completeness | "Deforming geo on /obj/character but no motion blur enabled." |
| AOV check | "Missing diffuse_direct AOV — Nuke comp will need it." |

| Camera check | "No camera assigned to ROP / camera has zero resolution." |

**Implementation: 1 file**


Follows the same pattern as scene_doctor: structured report, severity levels,
auto-fix where possible. Focused specifically on render pipeline.

### ERROR TRANSLATOR

**What it does:** Intercepts Houdini error messages and translates them into
human-readable explanations with suggested fixes.

**This is invisible infrastructure.** No slash command — it activates
automatically when the artist encounters an error and asks SYNAPSE about it,
or when a tool execution returns an error.

**Implementation approach:** A lookup table of common error patterns mapped
to plain-English explanations, plus a fallback that sends the raw error to
Claude with node context for interpretation.

```python
ERROR_PATTERNS = {
    r"SOP_AttribCreate.*invalid group": {
        "explain": "The group field references a group that doesn't exist on the incoming geometry.",
        "suggest": "Check available groups with /inspect on the input node.",
        "auto_fix": None,  # needs user decision
    },
    r"Unable to read file (.+)": {
        "explain": "Houdini can't find the file at {match_1}.",
        "suggest": "Check if the file exists. If it moved, update the path.",
        "auto_fix": "search_for_file",
    },
    r"Cook error.*maximum recursion": {
        "explain": "A node is referencing itself in a loop, causing infinite recursion.",
        "suggest": "Look for circular channel references or SOP dependencies.",
        "auto_fix": None,
    },
}
```

**The fallback is the real power:** When no pattern matches, SYNAPSE sends
the error + node info + network context to Claude and gets a natural language
explanation. Over time, the pattern table grows from what Claude explains.

### EXPLAIN MODE — `/explain`

**What it does:** Select any node or network, type `/explain`. SYNAPSE reads
everything about it and explains in plain English.

**What it reads:**
- Node type and its documentation
- Current parameter values (not defaults — what's actually set)
- Input connections and what data they carry
- Output data (point count, prim count, attribute list)
- Cook time
- Any errors or warnings
- Position in the network (what's upstream, what's downstream)

**What it produces (example):**

> **mountain1** (Mountain SOP)
>
> This node adds procedural noise displacement to the incoming grid.
> It's pushing vertices up and down based on a noise pattern — think of it
> like crumpling a sheet of paper, but mathematically controlled.
>
> Right now it's set to:
> - Height: 3.5 (how tall the peaks get)
> - Element Size: 2.0 (how wide each mountain — bigger = smoother hills)
> - Roughness: 0.6 (how jagged — 0 is smooth rolling, 1 is sharp peaks)
> - Offset: animated (it's moving over time — that's why the terrain drifts)
>
> It's receiving a 200×200 grid (40,000 points) from grid1 above, and feeding
> into a color SOP below that's painting based on height.
>
> Cook time: 2.3ms — very fast, no concern here.

**The key insight:** This isn't documentation. Documentation tells you what
a Mountain SOP *can* do. SYNAPSE tells you what *this particular one* is
*actually doing* in *your scene*.

**Implementation:**

```
python/synapse/panel/explain_mode.py

Function: explain_node(node_path: str) -> str
  - Get node type info (hou.nodeType.description())
  - Get all non-default parameter values
  - Get input/output geometry stats
  - Get cook time from performance monitor
  - Get errors/warnings
  - Build a structured context dict
  - Send to Claude with a "explain this node for a Houdini artist" prompt
  - Return the explanation

Function: explain_network(network_path: str) -> str
  - List all nodes in order of data flow
  - For each: type, key parms, connections
  - Send to Claude with "explain this network as a data flow"
  - Return the walkthrough
```

### NETWORK TRACE — `/trace`

**What it does:** Follows data from the top of a network to the display node,
narrating each transformation.

**Output (example):**
> **Data flow in /obj/geo1:**
>
> 1. **grid1** — Creates a 50×50 polygon grid (2,500 points, 2,401 quads)
> 2. **mountain1** — Displaces Y position with turbulent noise. Peak height: 5.0.
>    Points: 2,500 → 2,500 (no change). New attribute: none. Time: 1.2ms.
> 3. **attribwrangle1** — Custom VEX: colors points by height using a ramp.
>    Reads: @P.y. Writes: @Cd. Points: 2,500. Time: 0.4ms.
> 4. **scatter1** — Distributes 10,000 random points on the surface.
>    Points: 2,500 → 10,000. Inherits: @Cd, @N. Time: 3.1ms.
> 5. **copytopoints1** — Copies tree_geo (input 2: 1,200 pts) onto each scatter point.
>    Points: 10,000 × 1,200 = 12,000,000. ⚠️ This is heavy. Time: 890ms.
>
> **Total: 895ms cook time. Bottleneck: copytopoints1 (99.4%)**

**This is how you learn Houdini.** Not by reading docs — by watching data
flow through a real network with real numbers.

### VEX TUTOR — `/vex`

**Three modes:**

`/vex explain` — Select a wrangle, explains the code line by line with context.

`/vex help {concept}` — Quick reference: `/vex help pcfind` explains the function
with a practical example using the artist's actual geometry.

`/vex write {description}` — "Color points by distance from the center" →
writes the VEX snippet AND explains each line as it writes it.

**Key principle:** Never just give code. Always explain *why* this approach.
"We're using `length(@P)` instead of `distance(@P, {0,0,0})` because
when measuring from origin, length is faster — it skips the subtraction."

**Organized by context, not alphabet:**

**Recipes are extensible.** The artist can `/recipes add "my displacement technique"`

## SPRINT 4: APEX DEEP DIVE

**Theme:** Make APEX approachable. It's the future of Houdini rigging and
almost nobody understands it yet. First-mover advantage for SYNAPSE.

---

### APEX EXPLAINER — `/apex explain`

APEX introduces concepts that don't exist anywhere else in Houdini:

| Concept | What Artists Think | What It Actually Is |
|---------|-------------------|-------------------|
| APEX Graph | "Some kind of VOP network?" | An execution program stored as geometry |
| Packed Folder | "Packed geo?" | A container for rig components — like a namespace |
| Invoke SOP | "Runs something?" | Executes an APEX graph on input geometry |
| Rig Logic vs Rig Execution | "???" | Logic = how to build the rig. Execution = evaluating it per frame. |
| APEX Autorig | "Magic?" | A set of pre-built APEX graphs for standard rig tasks |
| Character Definition | "A rig?" | A structured packed folder hierarchy that defines rig structure |

`/apex explain` on any APEX node gives the Mariana Trench guide explanation:

> **apex::invoke1** (APEX Invoke)
>
> Think of this as a "run program" button. The "program" is an APEX graph
> stored as packed geometry coming in from input 1. That graph describes
> a sequence of operations — like a VEX wrangle, but visual and graph-based.
>
> Right now it's running an FK solver graph on the skeleton coming from
> input 0. The graph reads joint transforms, applies FK rotations from
> control channels, and writes the result back to the skeleton.
>
> The key mental model: APEX graphs are *programs stored as geometry*.
> They travel with your scene, they're inspectable, and they compose.

---

### APEX RECIPES

Production-ready APEX setups buildable via /hda or direct execution:

| Recipe | What It Builds |
|--------|---------------|
| FK Chain | Curve → joints → FK controls → APEX graph |
| IK Chain | Curve → joints → IK solver → pole vector control |
| FK/IK Blend | Combined chain with blend control |
| Autorig Character | T-pose → APEX Autorig → full character rig |
| Facial Rig | Points → blend shapes → APEX control graph |
| Muscle System | Joints → muscle primitives → deform |
| Custom Deformer | Input geo → APEX deformer graph → output |
| KineFX Conversion | Existing KineFX rig → equivalent APEX setup |

Each recipe includes:
- The node network to build
- An `/explain` walkthrough of each step
- Key parameter descriptions
- "What to tweak first" guide

---

### APEX GRAPH TRACE — `/apex trace`

APEX graphs are hard to debug because execution is opaque.

`/apex trace` on an Invoke node:
1. Reads the APEX graph from packed geometry
2. Lists all nodes in execution order
3. For each node: what it computes, what it reads, what it writes
4. Highlights the critical path (slowest evaluation chain)
5. Shows data flow between rig components

This is tooling that *doesn't exist yet*. SideFX has basic graph visualization
but no step-by-step narrated trace. SYNAPSE would be the first.

## Implementation Priority Guide

**If you have 1 sprint after tool parity:** Sprint 2 (Safety Net).
Trust precedes everything.

**If you have 2 sprints:** Sprint 2 + Sprint 3 (Knowledge Transfer).
Safety + learning = artists who are confident AND growing.

**If you're targeting a demo:** Sprint 2's /diagnose + Sprint 3's /explain +
Sprint 1's /hda. Those three in a 60-second video tell the whole story:
"SYNAPSE catches your mistakes, teaches you new things, and builds what you ask for."

**If you're targeting studios:** Sprint 6 (Production Pipeline) becomes
Sprint 2. Studios care about /deps, /profile, and save-shot more than
/explain. Reorder based on audience.

**The APEX sprint** is a market differentiator. Nobody is doing AI-assisted
APEX workflows. Being first here while APEX adoption is still early
means SYNAPSE becomes *the way* people learn APEX.
