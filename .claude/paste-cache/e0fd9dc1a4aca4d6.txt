## Agent 1: HDA-from-Prompt Tools

**Objective:** Add MCP tools that let Claude package any generated node network into a reusable HDA with proper interface, help card, and installation.

### New MCP Tools

#### `hda_create`
Create an HDA definition from an existing subnet or selection.

```python
# Tool signature
{
    "name": "hda_create",
    "description": "Create a Houdini Digital Asset from a subnet node. Wraps the subnet into an HDA with a proper operator type name, label, and version.",
    "parameters": {
        "subnet_path": "str  # Path to the subnet to convert, e.g. /obj/geo1/my_subnet",
        "operator_name": "str  # Internal name, e.g. 'sop_scatter_on_terrain'",
        "operator_label": "str  # Display name, e.g. 'Scatter on Terrain'",
        "category": "str  # Node category: Sop, Object, Driver, Lop, Top, etc.",
        "version": "str  # Semver string, default '1.0.0'",
        "save_path": "str  # Where to save the .hda file, e.g. '$HIP/hda/scatter_on_terrain.hda'",
        "min_inputs": "int  # Minimum connected inputs (default 0)",
        "max_inputs": "int  # Maximum connected inputs (default 1)",
        "icon": "str  # Optional icon name from Houdini icon set"
    }
}
```

**Implementation notes:**
- Use `node.createDigitalAsset()` which handles the subnet → HDA conversion
- Set `hou.HDADefinition` metadata (author, version, timestamp)
- Register with `hou.hda.installFile()` after creation
- **Safety:** Undo group wrapping. Validate subnet exists before conversion. Check save_path is writable.

#### `hda_promote_parm`
Promote internal parameters to the HDA interface.

```python
{
    "name": "hda_promote_parm",
    "description": "Promote an internal node parameter to the HDA's top-level interface. This makes the parameter visible and editable on the HDA itself.",
    "parameters": {
        "hda_path": "str  # Path to the HDA instance",
        "internal_node": "str  # Relative path to internal node, e.g. 'scatter1'",
        "parm_name": "str  # Parameter name on the internal node",
        "label": "str  # Optional display label override",
        "folder": "str  # Optional folder/tab to organize into",
        "callback": "str  # Optional Python callback script",
        "conditions": "dict  # Optional visibility conditions"
    }
}
```

**Implementation notes:**
- Use `hou.HDADefinition.setParmTemplateGroup()` to modify the interface
- Build `hou.ParmTemplate` objects that reference internal parameters via channel references
- Support grouping promoted parms into folders/tabs for clean UX
- **Safety:** Validate the internal node and parm exist. Idempotent — re-promoting same parm updates rather than duplicates.

#### `hda_set_help`
Set the HDA's help card / documentation.

```python
{
    "name": "hda_set_help",
    "description": "Set the help text and documentation for an HDA. Generates a help card visible in Houdini's help browser.",
    "parameters": {
        "hda_path": "str  # Path to the HDA instance",
        "summary": "str  # One-line description",
        "description": "str  # Full description (supports Houdini wiki markup)",
        "parameters_help": "dict  # {parm_name: help_text} for each promoted parameter",
        "tips": "list[str]  # Optional usage tips",
        "author": "str  # Optional author name"
    }
}
```

**Implementation notes:**
- Use `hou.HDADefinition.setComment()` for summary
- Use `hou.HDADefinition.addSection()` with `DialogScript` help format
- Houdini help uses a wiki-like markup — generate it from the structured input
- **Safety:** Read-only operation on the scene graph. Low risk.

#### `hda_package` (Compound Tool)
High-level orchestrator that creates an HDA from a description in one shot.

```python
{
    "name": "hda_package",
    "description": "Full HDA creation pipeline: builds internal network, promotes key parameters, generates help card, saves and installs. This is the 'HDA from prompt' entry point.",
    "parameters": {
        "description": "str  # Natural language description of what the HDA should do",
        "name": "str  # Desired HDA name",
        "category": "str  # Sop, Object, Driver, Lop, Top",
        "save_path": "str  # Where to save, e.g. '$HIP/hda/'",
        "complexity_hint": "str  # 'simple' | 'moderate' | 'complex' — guides network generation"
    }
}
```

**Implementation notes:**
- This is an agent-orchestrated multi-step tool, NOT a single atomic operation
- Step flow:
  1. Create a subnet at a temp location
  2. Generate internal network using existing node creation tools
  3. Identify key parameters to promote (Claude reasoning step)
  4. Call `hda_create` to package
  5. Call `hda_promote_parm` for each key parameter
  6. Call `hda_set_help` with auto-generated documentation
  7. Clean up temp nodes
- **Safety:** The entire flow runs inside a single undo group. If any step fails, everything rolls back.
- **Memory integration:** Log the created HDA to scene memory (what was built, why, parameter choices)

#### `ws_client.py` — WebSocket Client

```python
# QThread-based WebSocket client that:
# - Connects to ws://localhost:9999
# - Sends JSON messages (same protocol as existing MCP)
# - Emits Qt signals on message received
# - Auto-reconnects with backoff
# - Shows connection status in context bar

class SynapseWSClient(QThread):
    message_received = Signal(dict)   # Emitted when server responds
    connection_changed = Signal(bool) # Emitted on connect/disconnect

    def send_message(self, text: str, context: dict = None):
        """Send a user message with optional scene context."""
        payload = {
            "type": "chat",
            "message": text,
            "context": context or self._gather_context()
        }
        self.ws.send(json.dumps(payload))

    def _gather_context(self) -> dict:
        """Auto-gather current selection, node path, etc."""
        return {
            "selected_nodes": [n.path() for n in hou.selectedNodes()],
            "current_network": hou.ui.paneTabOfType(hou.paneTabType.NetworkEditor).pwd().path(),
            "scene_file": hou.hipFile.path()
        }
```

**Key design decisions:**
- Use `QThread` not `asyncio` — Houdini's Qt event loop doesn't play well with asyncio
- Context auto-gathering happens on every message send, so Claude always knows what the artist is looking at
- The WS protocol mirrors existing MCP message format for zero server-side changes

## Agent 3: Network Explainer Tool

**Objective:** An MCP tool that walks a node network and produces a structured, plain-English explanation. Feeds into both the chat panel and HDA documentation generation.

### MCP Tool

#### `network_explain`

```python
{
    "name": "network_explain",
    "description": "Walk a Houdini node network and produce a structured explanation. Describes what each node does, how data flows, and what the overall network achieves. Output can feed into HDA help generation or be displayed directly to the artist.",
    "parameters": {
        "root_path": "str  # Path to the network root, e.g. '/obj/geo1'",
        "depth": "int  # How deep to traverse (default 2, max 5)",
        "detail_level": "str  # 'summary' | 'standard' | 'detailed'",
        "include_parameters": "bool  # Include key parameter values (default true)",
        "include_expressions": "bool  # Include channel expressions (default false)",
        "format": "str  # 'prose' | 'structured' | 'help_card'"
    }
}
```

**Implementation approach:**

```python
def network_explain(root_path, depth=2, detail_level="standard", ...):
    """
    Walk strategy:
    1. Get all child nodes of root_path
    2. Build a dependency graph (input/output connections)
    3. Topological sort to get data flow order
    4. For each node in flow order:
       - Identify node type and look up from VEX CORPUS / node database
       - Read key parameters (non-default values only for 'summary')
       - Note any expressions or references
    5. Identify the overall pattern:
       - Is this a scatter workflow?
       - Is this a simulation setup?
       - Is this a material assignment chain?
    6. Generate explanation in requested format
    """

    # Output structure:
    return {
        "overview": "This network creates a procedural rock scatter...",
        "data_flow": [
            {
                "node": "grid1",
                "type": "SOP Grid",
                "role": "Creates the base terrain surface",
                "key_params": {"rows": 50, "cols": 50, "size": [10, 10]},
                "outputs_to": ["mountain1"]
            },
            # ...
        ],
        "patterns_detected": ["scatter_workflow", "copy_to_points"],
        "complexity": "moderate",
        "suggested_hda_interface": [
            # Parameters worth promoting if this becomes an HDA
            {"node": "scatter1", "parm": "npts", "reason": "Controls density"},
            {"node": "mountain1", "parm": "height", "reason": "Controls terrain roughness"}
        ]
    }
```

**Key insight:** The `suggested_hda_interface` field directly feeds `hda_package`. When an artist says "make this an HDA," the explainer has already identified which parameters matter. This closes the loop between P0 and P2.

## Agent 4: Integration & Wiring

**Runs after Agents 1-3 complete.** Wires everything together and validates end-to-end flows.

### Integration Points

#### Panel → HDA Pipeline
```
Artist selects subnet
  → Clicks "Make HDA" quick action
  → Panel sends to SYNAPSE with selection context
  → Claude calls network_explain (gets structure + suggested interface)
  → Claude calls hda_package (builds the HDA)
  → Panel shows result with link to new HDA
  → HDA appears in artist's tab menu
```

#### Panel → Explain Pipeline
```
Artist selects nodes
  → Clicks "Explain" quick action
  → Panel sends to SYNAPSE with selection context
  → Claude calls network_explain
  → Panel renders explanation with clickable node paths
  → Artist clicks a node path → Houdini navigates to that node
```

#### Explain → HDA Help Pipeline
```
network_explain output (format='help_card')
  → Fed directly into hda_set_help
  → HDA ships with auto-generated documentation
```

## Notes for Claude Code Agents

**Conventions to follow:**
- Atomic scripts (one mutation per call)
- Idempotent guards (check-before-mutate)
- Undo group wrapping on all scene-mutating operations
- SHA-256 manifest tracking for new files
- Collision-safe prefixing for any generated content
- Type hints + mypy compliance on all new code
- Server-side message rewrites maintain supportive tone

**Do NOT:**
- Break any existing tests
- Modify existing MCP tool signatures
- Change the WebSocket protocol (panel adapts to existing protocol)
- Add external dependencies (zero-dependency principle)

**Reference:**
- Existing tool patterns: `synapse/tools/` (43 tools as template)
- Test patterns: `tests/` (1,012 existing tests as reference)
- WS protocol: `synapse/server/ws_handler.py`
- Memory system: `synapse/memory/`
- Voice guide: `synapse/voice/`
